# Spec Factory Design

## Goal

Build a new Spec Factory service and Dashboard page that turn Louise-estimated raw client requirement tickets into OneShot-ready Jira Epics and child Story/Task tickets.

The first production workflow is `Louise`, driven by:

```jql
labels = "louise-estimated"
```

`Compose` is a future workflow for freeform raw material such as meeting notes, rough ideas, and PRDs. `OneShot` is the tracking workflow for generated child tickets after they have been submitted into OneShot.

## Current OneShot Contract

OneShot should receive normal Jira Story/Task/Bug tickets, not raw requirement tickets and not broad Epics.

Each OneShot-submitted child ticket must be self-contained and include:

- `PFOS` label.
- Clear bounded summary.
- Overview or description.
- Acceptance criteria.
- Technical details with an explicit `Repo:` line and optional `Branch:` line.
- Out-of-scope and testing notes when known.

The generated Epic should organize the business requirement and cross-repo delivery context, but the Epic itself should not get `PFOS`. `PFOS` belongs on the child Story/Task tickets because the live OneShot qualifier creates one repo-bound run at a time.

## Product Model

Spec Factory has one shell with three side-nav sections:

- `Compose`: future intake and clarification chat. Out of scope for the MVP except for a disabled or placeholder nav item.
- `Louise`: primary MVP workflow. Displays tickets returned by the Louise JQL as a storyboard/Kanban of sticky-note cards.
- `OneShot`: shows work generated by Spec Factory and already submitted into OneShot.

The Louise source ticket is the unit shown on the board. In the MVP, one Louise source ticket generates one Epic bundle. A bundle contains:

- One generated Jira Epic draft.
- One or more generated child Story/Task drafts, normally one per repo involved.
- An evidence manifest that maps raw requirements, LOE hours, code-change attachments, config-change attachments, estimate material, and independently inspected repository context to generated Epic and story content.

Multi-source-ticket bundling can be added later, but it is not part of the first implementation.

## Repository Grounding

Spec Factory must not treat Louise attachments as the complete source of truth. The LOE documents are strong starting evidence because they often name repositories, code files, config files, and estimated effort, but draft generation must also inspect current repository state before writing OneShot-ready requirements.

Spec Factory gets its own dedicated EFS-backed repository area, parallel to the existing OneShot and Specter agent worktree setups. The default layout is:

- Repo cache: `/mnt/efs/specter-repo/oneshot/repos` shared with OneShot
- Per-source workspaces: `/mnt/efs/specter-repo/spec-factory/workspaces`

Spec Factory first grounds against `master` for every repository it inspects. If `master` is missing, it uses `main`. It must not infer or use customer, release, or source-ticket branch names for the MVP, even when the Louise attachment mentions another branch. If a repository has neither `master` nor `main`, the source should move to `needs_attention` with a clear warning rather than silently drafting from a different branch.

The repository grounding pass should:

- Use repo names and file hints extracted from Louise evidence to identify likely repositories.
- Refresh or clone the repo cache from GitHub into the Spec Factory EFS area.
- Create a read-only per-source worktree or checkout pinned to `origin/master` or, when `master` is missing, `origin/main`.
- Inspect relevant files, nearby config, tests, and ownership/context files.
- Produce a compact repo context manifest with repo name, selected branch (`master` or `main`), head SHA, inspected paths, relevant snippets or summaries, warnings, and unresolved hints.

Draft generation receives both the Louise evidence manifest and the repo context manifest. Generated child tickets should cite both source evidence and observed repo context where possible. The generator should prefer verified current code/config over stale attachment claims when they conflict, while preserving conflicts as notebook warnings for the operator.

## Attachment Evidence Store

Louise source tickets can include LOE estimates, code-change notes, config-change notes, screenshots, documents, spreadsheets, SQL, logs, and other raw client material. Spec Factory must not rely on transient Jira downloads as the only copy of this evidence.

Every attachment discovered on a Louise source ticket should be downloaded and persisted to S3 before Epic preview generation. The database should retain an attachment manifest for each source ticket, including Jira attachment id, filename, MIME type, size, checksum, S3 bucket/key, download status, processing status, extracted text status, and any error or skip reason.

The preview generator should consume processed attachment evidence from the Spec Factory attachment manifest, not from an ad hoc live Jira fetch. Raw binaries stay in S3; extracted text, structured summaries, and processing warnings are persisted in the database and included in the evidence manifest used by draft generation. If an attachment cannot be downloaded or processed, the notebook should show the gap clearly and generation should decide whether the missing evidence is blocking or non-blocking based on attachment type and ticket context.

## Louise Board

The Louise board fetches candidate source tickets with `labels = "louise-estimated"` and filters out source tickets already submitted through Spec Factory.

Each sticky-note card shows:

- Jira key.
- Short summary.
- LOE hours.
- Draft state.
- Generated Epic key, if already approved.
- Submission state, if already OneShotted.

Recommended board columns:

- `Ready`: source ticket has Louise estimate material but no generated draft yet.
- `Draft Ready`: Spec Factory has generated a preview bundle.
- `Approved`: Epic and child stories exist in Jira, but child stories have not been sent to OneShot.
- `Needs Attention`: generation, Jira creation, or submission failed and needs operator retry.

After `OneShot Now` succeeds for a source ticket, the card no longer appears on the Louise board. It appears in the `OneShot` view instead.

## Notebook Preview

Selecting a sticky-note opens a right-side notebook panel. The notebook is read-first and action-oriented.

The MVP notebook has pages for:

- Source ticket summary: raw requirement, current Jira status, source links, LOE hours.
- Generated Epic preview: Epic summary, business context, scope, assumptions, dependencies, and acceptance summary.
- Child stories: one page or section per generated repo-specific Story/Task.
- Evidence: Louise/LOE artifacts, code-change attachments, config-change attachments, comments, and any parsing warnings.

Operators can scroll through notebook pages. Later, if multi-source Epic composition is added, the notebook can become one source ticket per page inside a larger Epic bundle. The MVP keeps one selected source ticket per notebook.

Primary notebook actions:

- `Generate / Refresh Draft`: produce or regenerate the preview bundle.
- `Approve Epic`: create the Epic and child Story/Task tickets in Jira. This does not add `PFOS`.
- `OneShot Now`: add `PFOS` to the generated child Story/Task tickets and submit them to OneShot.

`OneShot Now` is disabled until the Epic has been approved and Jira keys exist for all generated child tickets.

## Approval And Submission Semantics

`Approve Epic` is the Jira creation step.

It creates:

- One Epic.
- One child Story/Task per repo involved.

The generated child descriptions must include the exact OneShot-ready template content. They should be good enough for QUALIFIER to route without reading the Epic.

Labels:

- Epic: `SPEC-FACTORY`, `SPEC-FACTORY-GENERATED`.
- Child Story/Task before OneShot: `SPEC-FACTORY`, `SPEC-FACTORY-GENERATED`.
- Child Story/Task after `OneShot Now`: add `PFOS`.

`OneShot Now` is the automation trigger. It adds `PFOS` to the generated child tickets and records that the source bundle has been submitted. If the dashboard run-request path is available, Spec Factory should also create run requests for the child tickets so QUALIFIER starts promptly. If not, label-based polling remains the fallback.

All mutation actions must be idempotent:

- Re-running `Approve Epic` must not create duplicate Epics or duplicate child stories.
- Re-running `OneShot Now` must not duplicate labels or duplicate active run requests.
- Partial failures must be visible and retryable from the notebook.

## Backend Architecture

Spec Factory runs as a new ECS service. It should live in the same repository and reuse the existing TypeScript, database, Jira, and dashboard patterns.

Recommended backend modules:

- `CandidateIngestor`: runs the configured JQL, fetches source Jira tickets, and stores source snapshots.
- `EvidenceCollector`: reads issue description, comments, attachments, and Louise/LOE output material. It should reuse `JiraClient.fetchTicketData()` behavior where possible.
- `RepoWorkspaceManager`: manages the dedicated Spec Factory EFS repo cache and per-source `master` or `main` branch workspaces.
- `RepoContextCollector`: inspects current `master` or `main` code/config for repos suggested by Louise evidence and produces compact grounding context.
- `DraftGenerator`: calls the LLM to produce a structured Epic bundle draft from the source snapshot, evidence manifest, and repository context manifest.
- `DraftValidator`: verifies the generated bundle before preview or approval. It enforces one child per repo, OneShot ticket sections, `Repo:` lines, acceptance criteria, and missing-evidence warnings.
- `JiraPublisher`: creates the Epic and child Story/Task tickets, links them to the source ticket, and stores created Jira keys.
- `OneShotSubmitter`: adds `PFOS` to generated child tickets and creates OneShot run requests when available.
- `SpecFactoryApi`: exposes Dashboard endpoints for candidates, draft preview, approval, submission, and submitted work tracking.

The service should not modify raw Louise source tickets as its primary state mechanism. Local Spec Factory tables should determine whether a source ticket is still on the board. Jira comments or trace labels can be added as audit aids, but they should not be required for correctness.

## API Shape

Initial Dashboard-facing endpoints:

- `GET /api/spec-factory/louise/candidates`
- `POST /api/spec-factory/louise/refresh`
- `POST /api/spec-factory/sources/:sourceId/drafts`
- `GET /api/spec-factory/sources/:sourceId/drafts/latest`
- `POST /api/spec-factory/drafts/:draftId/approve`
- `POST /api/spec-factory/sources/:sourceId/oneshot`
- `GET /api/spec-factory/oneshot/submissions`

Responses should include both machine state and UI-friendly display fields so the Dashboard does not need to infer workflow state from raw Jira payloads.

## Dashboard Design

Add a new top-level Dashboard route for Spec Factory.

The Spec Factory page owns its side nav:

- `Compose`
- `Louise`
- `OneShot`

`Compose` can render a clearly disabled or empty state in the MVP.

`Louise` renders:

- Header with JQL and refresh action.
- Board columns with sticky-note source cards.
- Right-side notebook panel for the selected card.
- Action buttons inside the notebook.
- Inline retry/status messages for failures.

`OneShot` renders:

- Generated Epic key.
- Source Jira key.
- Child Story/Task keys.
- Repo names.
- OneShot run state when available.
- Link back to the source bundle notebook.

The page should feel like an operational tool, not a landing page. Use dense but readable information, restrained styling, predictable nav, and direct actions.

## Error Handling

Candidate ingestion errors:

- Keep the last successful board state if refresh fails.
- Surface the refresh error in the Louise header.

Missing or incomplete LOE evidence:

- Keep the source card visible.
- Generate a draft only if enough requirement context exists.
- Show notebook warnings for missing `loe-estimate`, `code-changes`, or `config-changes` artifacts.

Draft generation errors:

- Mark the source as `needs_attention`.
- Preserve source evidence and error message.
- Allow retry from the notebook.

Jira approval partial failure:

- Store every Jira key created before the failure.
- Retry should continue from the stored keys, not recreate them.
- Show exactly which child story failed.

OneShot submission partial failure:

- Add `PFOS` only to child tickets not already labeled.
- Store per-child submission state.
- Allow retry for failed children.

## Security And Controls

Spec Factory needs Jira read and mutation access. It should use existing Jira credential patterns and respect existing mutation guard behavior where applicable.

Operator actions should be auditable through `spec_factory_events`.

The MVP should not auto-submit to OneShot on draft generation or approval. Only the explicit `OneShot Now` action triggers `PFOS`.

## Testing Strategy

Unit tests:

- LOE/evidence extraction from Jira ticket data.
- Draft validation rules.
- OneShot child ticket rendering.
- State transitions for approval and submission.
- Idempotency for approve and submit.

Service tests:

- Candidate refresh with mocked Jira search.
- Draft generation with mocked LLM output.
- Approval with mocked Jira create issue responses.
- OneShot submission with mocked label/run-request calls.

Dashboard tests:

- Louise board renders candidate cards with LOE hours.
- Selecting a sticky note opens notebook pages.
- `Approve Epic` is disabled until draft is ready.
- `OneShot Now` is disabled until Jira keys exist.
- Submitted source ticket disappears from Louise board and appears in OneShot view.

Manual verification:

- Run the Dashboard locally.
- Refresh Louise candidates.
- Generate a draft from a mocked or lower-environment ticket.
- Approve the Epic in a safe environment.
- Submit to OneShot and verify the generated child tickets receive `PFOS`.

## Approach Options Considered

### Option A: Send Raw Louise Tickets Directly To OneShot

This is the smallest backend change, but it pushes raw, broad, multi-repo requirements into OneShot. It conflicts with the current OneShot expectation that each run is single-repo and ticket text is already bounded.

### Option B: Generate One Epic With Child Story/Task Tickets

This matches the current OneShot contract. The Epic carries the business context while child tickets are self-contained OneShot inputs. It also matches the desired UI and keeps the operator in control through `Approve Epic` and `OneShot Now`.

### Option C: Use Jira Sub-tasks Per Repo

This can look attractive structurally, but it does not fit the current OneShot reporting/query path as well as normal Epic children. It also risks Jira project-specific issue type behavior.

## Recommendation

Use Option B for the MVP.

Build the Louise workflow first, with one source ticket producing one Epic bundle and one child Story/Task per repo. Keep `Compose` as a placeholder and build `OneShot` as the submitted-work tracking view.
