# End-to-End Checklists

Use this file when you want the shortest operational path after reading the detailed docs.

## Fresh-session bootstrap checklist

1. Read `agent-docs/00-MEMORYBANK.md`.
2. Read `agent-docs/01-CURRENT-STATE.md`.
3. Confirm current git state with:
   - `git status -sb`
   - `git rev-parse HEAD`
   - `git ls-remote origin refs/heads/main`
   - for migrated product repos, do not assume the default branch is `main`; verify `main` vs `master` before changing branch logic
4. Confirm the branch contains:
   - `terraform/shared.auto.tfvars`
   - the map-driven worker Terraform model
   - the stable Lambda source-hash logic in `terraform/main.tf`
5. Confirm which GitHub Environments exist:
   - `specter-terraform-apply`
   - `specter-aws-operations`
6. Confirm repo AWS config still matches the documented values:
   - `AWS_ROLE_ARN`
   - `ECR_REGISTRY`

## Terraform change checklist

Before editing Terraform for a new agent, answer these questions:

1. Is this a normal new worker that only needs `cpu`, `memory`, and `desired_count`?
2. If yes, can I avoid a Terraform schema change and use the onboarding workflow instead?
3. If no, exactly what structural change is required?
   - env var
   - secret
   - IAM
   - network
   - richer worker schema
4. If I am extending worker schema, did I update:
   - `terraform/variables.tf`
   - `terraform/main.tf`
   - `terraform/ecs.tf`
   - `.github/scripts/manage-worker-agent-catalog.py`
   - the relevant workflows
   - docs
5. Am I keeping secrets in Secrets Manager instead of committing them?
6. Am I preserving the shared worker map model instead of creating one-off worker resources?
7. Did I keep Lambda hash logic stable and exclude generated bytecode?

## New agent code checklist

1. Decide whether the new agent is:
   - Claude SDK-first
   - hybrid
   - deterministic service flow
2. Choose names:
   - `agent_key`
   - `agent_name`
   - worker file/class
   - internal Claude SDK key if needed
3. Create the domain agent implementation in `src/agents/`.
4. Create the worker in `src/orchestrator/workers/`.
5. Ensure the worker file can resolve from `WORKER_TYPE`.
6. If the agent uses Claude SDK:
   - update `AgentType`
   - update `getOutputSchema()`
   - update `getToolSet()`
   - add a prompt to `AGENT_PROMPTS`
7. Add exports where appropriate.
8. Add env vars if required.
9. If the agent depends on automatic repo selection, review `src/orchestrator/RepoAnalyzer.ts`:
   - does the ticket family already route to the right repo set?
   - does the repo family need a new deterministic rule?
   - for MP-family work, does the wording need to route to `mp-web` or `mp-product-client-configs`?
10. Run local validation:
   - `npm run build`
   - `python3 .github/scripts/resolve-worker-entry.py --worker-type ...`

## Onboarding checklist

1. Make sure the code is ready and pushed to the target branch.
2. If the agent needs a repository that is not already in `code_repositories`, gather:
   - `repository_name`
   - `repository_url`
   - optional `repository_description`
   - `repository_default_branch`
3. Run `Ops / Terraform / Agent Onboard`.
4. Review the Terraform plan.
5. Approve apply through `specter-terraform-apply`.
6. Confirm:
   - ECS desired count is `0`
   - DB row exists
   - DB row is inactive
   - optional repository row exists if repository inputs were provided
7. Merge the onboarding catalog PR.

## Image push checklist

1. Run `Build / Worker / Manual Push`.
2. Provide:
   - `agent_key`
   - `worker_type`
3. Confirm the image exists in:
   - `specter/<agent_key>-worker`
4. If the service is already running and should pick up the new image immediately:
   - run `Ops / ECS / Force New Deployment`

## Activation checklist

1. Confirm the onboarding catalog PR is merged.
2. Confirm the worker module resolves.
3. Confirm the first image exists in ECR.
4. Run `Ops / Terraform / Agent Activate`.
5. Review the Terraform plan.
6. Approve apply.
7. Confirm:
   - ECS desired count is correct
   - `agents.is_active = true`
8. Merge the activation catalog PR.

## Post-activation verification checklist

1. Check ECS service health.
2. Check worker log group.
3. Confirm the orchestrator sees the active agent.
4. Confirm tasks can be assigned.
5. Confirm the worker produces result markdown in S3.
6. Confirm JIRA or Teams delivery path works for the intended source.

## Targeted redeploy checklist

1. Confirm the service name:
   - worker example: `my-agent` -> `MY-AGENT`
   - shared services: `ORCHESTRATOR`, `HARVEY`, `DASHBOARD`
2. Run `Ops / ECS / Force New Deployment`.
3. Provide:
   - `service_name`
   - `reason`
   - `wait_for_stable`
4. Approve through `specter-aws-operations`.
5. Confirm the service returns to stable state.

## Terraform plan/apply checklist

1. Confirm the repo branch contains the Terraform change you want reviewed or applied.
2. Run `Ops / Terraform / Plan Or Apply`.
3. Pick:
   - `plan-only` for review
   - `apply-approved-plan` for an approved apply path
4. Review the uploaded plan text artifact.
5. If the plan shows only `aws_lambda_function.agent_registry`, verify the branch contains the stable Lambda hash logic before approving apply.
6. If applying, approve through `specter-terraform-apply`.
7. Confirm the workflow summary reflects the intended change set.

## Current live-ops verification checklist

This is the short list a future session should re-check before treating the operator workflows as fully healthy:

1. `origin/main` still contains the governed-workflow implementation and grouped workflow names.
2. `AWS_ROLE_ARN` still points to the GitHub OIDC role for the shared dev account.
3. `ECR_REGISTRY` still equals `323960442001.dkr.ecr.us-east-2.amazonaws.com`.
4. The GitHub OIDC role still has EFS read permission.
5. `specter-terraform-apply` still exists and has reviewers.
6. `specter-aws-operations` still exists and has reviewers.
7. Run `Ops / Terraform / OIDC Smoke Test` if in doubt.
8. Run `Ops / Terraform / Plan Or Apply` in `plan-only` mode if in doubt.
9. Exercise `Ops / ECS / Force New Deployment` when validating operator access.
10. Remove old `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` secrets if they still exist and nothing depends on them.
